接手一个陌生仓库时，你真正需要的不是一份面面俱到的架构说明书，而是**一张能自己导航的地图**，加上一条通往你当前目标的路径。

RepoPilot 就是干这个的：它先扫出仓库的骨架，然后问清你要做什么，只深入相关的那部分代码。

## 它解决什么问题

一次性把整个仓库解释完，结果通常是两种失败：要么泛泛而谈，要么长到没人读。

RepoPilot 的做法相反：

- **先建图，再深入** —— 地图阶段不展开任何单个模块
- **目标驱动** —— 跑起来、改功能、排查问题、熟悉业务，四条路径各不相同
- **事实与推断分开** —— 目录结构是事实，「这个模块负责什么」是推断，会明确标注
- **覆盖边界如实交代** —— 读到哪里、哪些没读，一律写明

## 四个目标，四条路径

| 你的目标 | 它交付什么 |
| --- | --- |
| 跑起来 | 环境要求、安装命令、配置清单、启动命令、常见失败原因 |
| 改功能 | 改动点定位、影响面、相关测试位置、风险提示 |
| 排查问题 | 最短复现路径、相关日志与监控点、最近改动、可疑边界条件 |
| 熟悉业务 | 领域模型、核心链路、模块职责边界、术语表 |

目标没说清时它会先问，不会默认替你选。

## 一条硬性设计约束

RepoPilot 只解释仓库，不生成业务代码，也不评价代码好坏、不做技术选型建议。

这不是能力不够，而是**职责边界**：理解代码和改代码是两件事，混在一起会让输出变得不可信。理解之后要改，那是下一步的事。
