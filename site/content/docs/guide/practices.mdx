---
title: 使用最佳实践
description: 结合三段式加载、任务路由与停点机制，讲清怎样调用更准、更省、更可控。
---

RepoPilot 不是"敲一个命令就出报告"的工具，它是一份由 Agent 执行的**流程编排手册**。理解下面三条机制，用法会自然变清晰——否则大多数"不好用"其实是作用域没给对。

## 三条机制，决定所有用法

### 机制一：三段式加载，装得多不等于读得多

| 层 | 内容 | 何时进入上下文 |
| --- | --- | --- |
| 发现层 | frontmatter 的 name / description | 常驻，供宿主匹配意图 |
| 操作层 | SKILL.md 正文（路由表 + 主线 + 边界） | 意图命中后 |
| 细节层 | 命中的 `references/workflows/*.md` 与 adapter | 按当前任务按需读 |
| 工具层 | `scripts/inventory.py`、`assets/templates/*` | 需要目录索引或保存报告时 |

一个完整安装目录有数十个文件，但**单次调用真正进入上下文的通常只有 3～5 个**。SKILL.md 里明确写着"不加载所有资源来凑完整"。

推论：**不用担心装得重，但要在意让哪一层的资料被读对**——这正是下面"任务词 + 作用域"两个维度要做的事。

### 机制二：任务词是意图参数，不是宿主命令

`onboard`、`library`、`deep` 这些词**不会注册成宿主的子命令**，不装调度服务、不起子 Agent。它们只是给 Agent 的路由标签。

推论：**自然语言和命令完全等价**。"帮我熟悉这个项目" 与 `$repo-pilot onboard` 走同一条流程。但自然语言可以额外携带作用域信息，往往比光秃秃一个任务词更准。

### 机制三：每个任务都有明确的停点

`references/contracts/delivery.md` 为每个流程定义了"最低交付"与"到哪里停止"。停点不是能力不足，是**刻意的边界**——防止一次调用把整个仓库读穿。

推论：**它停下来的时候，通常是在等你给更具体的方向**，不是卡住了。

## 八个做法

### 一、用两个维度控制调用：任务词 × 作用域

任务词决定它**读哪份流程资料**，目标参数决定它**读多少仓库代码**。后者才是影响准确度与耗时的关键，也最容易被忽略。

```text
/repo-pilot library react-query
# 差：全仓扫，monorepo 下可能串到另一个应用

/repo-pilot library @tanstack/react-query apps/easyv-workspace
# 好：锁定应用，版本按该应用的 lockfile 解释

/repo-pilot library @tanstack/react-query apps/easyv-workspace 只看列表页刷新那一段
# 最好：连场景都锁定，它只读相关引用树与消费链
```

### 二、先建全局，再进局部

顺序应该是 `onboard → walkthrough → locate`。

原理：`onboard` 产出的**应用、版本、入口、阅读路线**是后续所有任务共享的上下文。任务衔接契约规定：从 onboard 切到 library/deep 时**沿用这些上下文，只补读缺少的证据，不重开全仓流程**。

反过来，一上来就 `deep`，它必须先补读应用与版本才能开始，反而更慢、更容易串错应用。

### 三、显式约束输出粒度

停点保证的是**下限**，不保证上限。你想收窄，就直接说：

```text
只给首屏，不要全量依赖表
只读一个节点，讲完等我确认
不要生成文件，先在会话里说
```

同理，想要更完整也要明确："自动模式，一次三个节点"、"把它整理成文档保存"。

### 四、盯住证据等级

证据契约把结论分成四级，看到"推断"就应该追问下一证据：

| 等级 | 含义 |
| --- | --- |
| 已确认（静态） | 本次真实读到源码/配置 |
| 推断 | 由结构或命名推测，未直接证实 |
| 未知 | 关键材料缺失，需要下一证据 |
| 已运行验证 | 实际执行过，有运行结果 |

静态边界是硬的：**首次不安装依赖、不执行目标脚本、不启动服务与数据库**。所以"接口是否真的连通"这类问题，需要你自己跑起来验证，再把结果回传——它会把那条结论从"推断"升级为"已运行验证"。这不是缺陷，是刻意的安全边界。

### 五、用 walkthrough 的节奏读代码

`walkthrough` 默认**一轮只讲一个节点**（自动模式最多三个）。这是刻意设计：一轮塞进三个以上节点，你能记住的比例会断崖式下降。

说"继续"一次推进一步，讲完会给你下一候选位置和理由。想加速就明说"自动模式，三个节点"。

### 六、保存要挑时机，之后用 refresh

默认**只在会话里展示，不写文件**。需要跨会话复用时明确说"保存到 `.repopilot/`"，会生成 `00-start-here.md` 加架构与技术栈文档，之后任何新会话先读它再增量核对。

代码改完后用 `/repo-pilot refresh` **增量复核**，而不是重跑 onboard。它会告诉你哪些章节受影响、哪些还没复核。

一个常见损失：分析完没保存就关掉会话——这一轮全部白做。

### 七、混合项目先指定应用

monorepo 里同仓的其他应用**不会自动成为主线**。不指定应用，它只能猜，容易把另一个 app 的目录当成你的业务链路。多组件库、多版本并存的项目尤其要注意（例如同时存在两套 UI 库时，版本必须按你指定的应用解释）。

### 八、定位不等于照改

`locate` 交付的是**候选改动点 + 该复核什么 + 照哪处同类实现 + 如何验证**，它不会直接改你的代码。

真正动手前先看它指的同类实现——那是团队既有约定，比它生成的建议更权威。

## 一个完整实战脚本

```text
/repo-pilot onboard                                 # ① 建全局，约一分钟
保存到 .repopilot/                                   # ② 落盘，防丢
继续                                                 # ③ 沿阅读路线走节点，可重复
/repo-pilot locate 在团队分组页加一个导出按钮          # ④ 带需求落地
（你自己改代码、跑服务验证，把结果回传）
/repo-pilot refresh                                  # ⑤ 增量复核知识
```

## 三个典型误用

| 误用 | 后果 | 正确做法 |
| --- | --- | --- |
| 一上来就 `/repo-pilot deep 这个项目怎么工作` | 范围无限大，产出空泛 | 先 onboard，再挑一个具体机制 |
| 分析完不保存就关会话 | 全部结论丢失 | 明确说"保存" |
| 让它"帮我装依赖跑起来看看" | 违反静态边界，会降级为静态结论 | 自己跑，把终端输出贴回给它 |
