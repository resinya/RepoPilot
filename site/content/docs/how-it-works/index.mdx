title: 它是怎么工作的
description: Agent 直接执行，按任务路由到具体流程，交付前过证据、输出与质量三道契约。

RepoPilot 的运行者是 Agent 本身。没有中间服务、没有能力探测入口、没有资源清单解释器——SKILL.md 被读过之后，就由 Agent 按流程读真实代码、下结论、标证据。

## 三段式加载

| 层 | 内容 | 何时进入上下文 |
| --- | --- | --- |
| 发现层 | frontmatter 的 name / description | 常驻，供宿主匹配意图 |
| 操作层 | SKILL.md 正文：任务路由表、主线、边界 | 意图命中后 |
| 细节层 | 命中的 `references/workflows/*.md`，以及适配与契约资料 | 按当前任务按需读 |
| 工具层 | `scripts/inventory.py`、`assets/templates/*` | 需要目录索引或保存报告时 |

这样设计的理由有两条：一是**上下文预算**——一次调用只读 3～5 个文件，避免几十份资料挤占分析空间；二是**避免结论被模板带偏**——先有真实读取，再决定用哪个模板组织。

## 任务路由

SKILL.md 提供 12 个任务词，每个对应一份 `references/workflows/*.md`：

| 用途 | 任务词 |
| --- | --- |
| 全局认知 | onboard、map、architecture、stack |
| 局部深入 | walkthrough、library、deep、trace |
| 落地与维护 | locate、standards、teach、refresh |

任务词是**意图参数，不是宿主命令**——不注册子命令、不装调度服务、不开启子 Agent。所以自然语言与命令等价："帮我熟悉这个项目" 和 `$repo-pilot onboard` 走同一条流程。

不指定任务词时默认 onboard。任务词决定读哪份流程，目标参数决定读多少仓库代码——二者的配合方式见[使用最佳实践](/docs/guide/practices)。

## 三道契约

每次交付前都要过这三份契约，它们决定产出的下限：

| 契约 | 约束什么 |
| --- | --- |
| 证据契约 | 结论必须分级：已确认（静态）/ 推断 / 未知 / 已运行验证 |
| 输出契约 | 文件命名、信息层级、保存目录与来源记录 |
| 质量契约 | 五条硬门槛，任一不过先纠正或缩小范围，分数不能抵消 |

质量门槛的第一条就是：**上手首屏必须有四维架构、核心技术职责、重要位置与下一步**。准确的未知与下一证据可以合格，伪造结论不合格。

## 任务衔接：切任务不重开

从 onboard 切到 library 或 deep、再切回来时，**不会重开一遍全仓分析**。衔接契约要求沿用已经确认的应用、版本、入口与阅读历史，只补读缺少的证据。

例如：上手时看到渲染入口 → 你问"这个状态库在这里怎么用" → 它带着当前页面、实际包版本与消费符号进入 library → 讲清使用链后**返回原目标**，说明这段解答对下一步（比如新增属性面板）意味着什么。

## 停点与降级

- `walkthrough` 默认一轮一个节点，自动模式最多三个；
- `locate` 只给定位卡，不改代码、不启动服务；
- `library` 讲到"本项目怎么用"即停，算法与内部生命周期归 `deep`；
- 典型链路断在外部实现时停下并给出断点，不为了完整而扫遍所有服务。

`scripts/inventory.py` 是可选的只读目录索引，只列候选与遍历覆盖，不读内容、不判框架、不写知识。缺 Python 时用宿主搜索能力完成探索，不会要求安装运行时。

关键未知如实标为未知并给出下一证据，不会用一条候选链假称闭环。
