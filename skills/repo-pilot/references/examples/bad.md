# 反例导航 — 碎片输出与虚假证据

| 场景 | 完整坏输出与修正 | 主要问题 |
| --- | --- | --- |
| 项目上手 | [项目反例](onboarding-bad.md) | 文档太多、同一条链拆散、没有开发定位路线 |
| 单个库学习 | [库学习反例](library-bad.md) | 百科代替项目用法、常用API冒充项目调用 |
| 范围/版本/流程切换/风格 | [边界反例](task-boundaries.md) | 局部问题被放大、丢失上下文、未知被图示补全 |
| 业务学习与配置跳过 | [业务反例](business-learning.md) | 全文件、百科或答题门槛代替小步理解 |
| 集中阅读与可视化 | [地图反例](interactive-map.md) | 核心信息要逐层点选、多文档拼装或字段只有data |

不是禁止多文件，而是禁止把同一个认知问题无理由拆散。可独立查表的附录可以保留；默认主线必须自足。

## 不要补全不存在的证据

- “有 Axios，所有请求自动加 Token。”声明不证明封装/调用。
- “渲染 OrdersPage，一定请求数据库。”渲染、事件和请求是不同关系。
- “入口 src/main.ts:1。”惯例不能替代真实定位，Next 可能是框架约定。
- “扫描完成，已完整理解。”目录遍历、源码阅读和业务理解范围不同。
- “读给你听，标记学习完成。”展示不证明理解。
- “自动恢复，记录放 Skill references。”记录属于目标项目，恢复要有真实记录。
- “先 npm install 和启动数据库来证明能跑。”首轮静态探索无此授权。

修正要缩小结论、补读来源或保留断点，不靠更多字段制造可信度。
