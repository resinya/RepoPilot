# 正反例：业务全貌 → 小步带读 → 跳过 → 需求定位

这是合成演练，不是 dtstack-account 的事实拷贝。场景采用当前 Skill 的 web-api 夹具；示意路径都应在正式输出中换成实读位置。用来校准阅读效果，不用这些句子代替项目分析。

## 1. 用户：先理解业务，不要上来讲代码

**正例输出**

这个工作区让用户查看订单列表。业务只有两块：浏览器负责请求并展示订单，API 负责读取订单并返回 JSON。当前数据是内存数组，不是数据库。

| 模块 | 用户/业务目标 | 负责什么 | 位置 |
| --- | --- | --- | --- |
| 订单页面 | 看有哪些订单 | 挂载后取数据，把每个 id 展示出来 | apps/web/src/Orders.tsx：Orders |
| 请求函数 | 获取列表 | 发出 GET /orders，处理非成功响应并解析JSON | apps/web/src/api.ts：listOrders |
| 列表接口 | 提供订单数据 | 接收请求、调用业务函数、编码JSON | apps/api/src/main.ts：app.get |
| 查询与存储 | 取得已有订单 | 复制 store 数组；没有持久化 | apps/api/src/service.ts、store.ts |

这些是职责分工，不表示请求先执行页面文件再执行整个 main 文件。一个动作的数据变化是：

| 步骤 | 输入及来源 | 处理 | 输出与消费者 |
| --- | --- | --- | --- |
| 页面发起 | 挂载事件，无查询入参 | effect 调用 listOrders | Promise，页面等待 |
| 网络边界 | 相对 URL /orders | fetch 发 GET；API 有同方法路径 | 接收部署未知，不能确认连通 |
| API 查询 | store 中的订单数组 | listOrders 返回浅拷贝 | 数组交回路由 |
| 响应显示 | 成功 JSON 响应 | response.json → setOrders → orders.map | 用户看到订单 id 列表 |

如果需求是“显示订单名称”，先核对服务输出有没有名称，再改页面显示；如果要“按条件筛选”，检查请求函数、路由参数和查询函数。代理部署未知需要下一证据，不能声称已跑通。

**反例输出**

“用了 React、Express，目录有 apps。React 支持 Hooks，Express 是 Node 框架。先打开 main.tsx 全文。然后另看四份文档了解请求、业务、返回、渲染。”

问题：有名词没有分工，有文件没有业务目标；用户必须跨文档拼链路。

## 2. 用户：文件太大，带我分段看

**正例输出**

现在只回答一个问题：页面怎么把请求结果变成列表状态？

```tsx
useEffect(() => {
  listOrders().then(setOrders);
}, []);
```

这是夹具原始 effect 的排版展开，不是对项目的改动。挂载时调用请求函数，成功结果交给 setOrders；此时还没解释请求如何跨网络，也没出现数据库查询。当前走到：页面挂载 → 请求函数 → 成功后更新状态。

下一步只看 api.ts 的 listOrders，说明 GET /orders 与失败响应如何处理。你说“继续”就推进这一步，不用先回答测验。

**反例**：粘贴整个页面和请求文件，再逐行讲 JSX、泛型、事件循环、HTTP、React 生命周期，最后要求答完五道题才继续。

## 3. 用户：配置整体知道了，跳过

**正例**：“配置细节跳过，回到订单业务。现在只看路由如何把请求交给 listOrders。”记录用户要求跳过，不登记为已验证理解。

**反例**：“根据规则必须把端口、日志、缓存和密码配置都枚举，否则不进入业务。”SOP失去了帮助用户理解的目标。

## 4. 用户：是不是所有功能都走同一条链

**正例**：先核对实际入口和消费者。列表、文件上传、消息消费若不同，就分成不同动作；同名接口不合并实现。只看到生成图表配置，不能说已经完成组件创建、保存和画布渲染。

**反例**：把登录、临时会话、本地用户、外部凭证、JWT和Cookie都当“用户数据”；把两个版本的回调拼进一个顺序图。
