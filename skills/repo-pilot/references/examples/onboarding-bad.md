# 反例：内容很多，新人仍不知道怎么开始

## 与正例相同的输入

同一个合成React可视化平台，同一个“属性面板增加字段”需求。以下是故意错误的交付，不得照做。

## 错误输出一：阶段等于文件数

    project-report/
      00-index.md
      01-react.md
      02-vite.md
      03-directories.md
      04-entry.md
      05-providers.md
      06-router.md
      07-layout.md
      08-canvas.md
      09-drag.md
      10-render.md
      11-fields.md
      12-requests.md
      13-rules.md
      14-reading.md

00-index的正文：“所有文件都很重要，请按顺序学习。”没有产品分工、主应用选择、需求入口或内部目录，只把导航责任交给新人。

## 错误输出二：相关信息故意分散

04-entry：“入口在entry.tsx，具体包装去看05。”
05-providers：“有QueryProvider和主题，路由在06。”
06-router：“/edit/:id指向Editor，外壳去看07。”
07-layout：“包含Canvas和Properties，各自去看08与11。”
11-fields：“字段通过action修改，保存见12。”
12-requests：“服务负责保存，规范见13。”
13-rules：“遵循团队规范。”没有真实规范或同类例子。

读者只想知道一个字段在哪改，却要在八份文件间跳转；同一条入口到页面的链被人为切断，没有改动面和验收前提。

## 错误输出三：细节抢占整体认知

08-canvas先讲150行坐标推导。
09-drag逐行讲每个回调。
10-render讲所有缓存/节点更新内部实现。
但从未说明“这个产品哪些应用负责管理、编辑、展示”，也没说新增字段属于哪个模块。

用户必须先学会整个渲染引擎才能开始小需求，主Skill与deep的范围失控。

## 错误输出四：目录与包名代替解释

“src是源码，components是组件，services是服务。”
“用了React、Query、拖拽库、UI库。”
没有用途、版本、已用API、真实位置和相邻实现。包被声明就被说成负责全部拖拽；同名本地包被当作registry包源码。

## 错误输出五：结论强于证据

“扫描完成，系统全链路已跑通。先安装、启动服务和数据库。”
“默认npm start；有前端路由守卫就说明后台鉴权没问题。”
没有执行记录/环境来源，静态分析被冒充运行验证。

## 应如何修正

| 原问题 | 修正到同一主文档的哪里 |
| --- | --- |
| 只有文件索引 | 开头产品/主应用与内部阅读目录 |
| entry/Provider/Router/Layout被拆 | 一章连续的入口到页面 |
| 字段、action、保存与规范分开 | 一张需求定位卡＋项目式开发章节 |
| 坐标/渲染算法占首轮 | 能力位置表，机制由deep按需深入 |
| 包名与路径没有意义 | 相关能力旁的概念/API/位置短卡 |
| 全量清单抢主线 | 有需要才附录，不要求新人读完 |
| 静态当动态 | 已读、未知、未执行分别说明 |

不是“多文件永远不好”；可独立查表的依赖索引或限定机制报告可以分开。坏处在于把同一认知问题拆散而无阅读主线。正确组织见 [完整正例](onboarding-good.md)。
