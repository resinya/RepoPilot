# 任务边界案例 — 看输出能否帮助下一步工作

## 如何使用

用于校准局部问题、内部流程切换、版本、动态边界与交付检查。下面全部是合成材料，代码只代表给定片段，不是任何企业仓库事实，也不是已执行的 Agent 行为测试。只读当前案例；完整主文结构看 [上手正例](onboarding-good.md) / [反例](onboarding-bad.md)，完整包学习看 [库正例](library-good.md) / [反例](library-bad.md)。

每案固定给原始请求、可见输入、正面结果、对应坏结果和验收。维护者运行行为验收时只把请求和输入交给执行方，不把正反答案混入输入；另行记录实际输出、宿主/版本、访问与操作、通过或偏差。

## 案例 1：用户只问一个 API，不生成整套文档

**原始请求**：“这个 `invalidateQueries` 在这里是什么意思？两三句话告诉我，不保存。”

**给定材料**：当前 app 为 web；锁文件依据是 Query 4；已读保存操作的片段 `queryClient.invalidateQueries({ queryKey: ['items'] })`。只确认到保存完成回调与列表的相同 key，没有运行。

**好的输出**：

> 它把匹配 `['items']` 的查询缓存标为失效，好比提醒列表“这份数据需要重新看一遍”。这里放在保存完成回调里，和列表使用的 key 对应；是否立即重新请求还取决于查询当时的状态和选项。当前是源码分析，没有运行验证。

如需对具体库行为下结论，仍要查对应版本的官方依据；材料不足时缩小解释，不从记忆填不存在的选项。

本例的通用 API 语义依据 [TanStack Query v4：Query Invalidation](https://tanstack.com/query/v4/docs/framework/react/guides/query-invalidation)，核对日期 2026-10-11。项目回调/key 对应关系来自给定合成输入，不由官方文档证明。

**坏的输出**：“先确认学习方向。已创建概念.md、API.md、缓存.md、项目地图.md。这里会清空所有缓存并刷新全站。”

**问题与验收**：回答请求的 API 和项目作用即可；不保存、不追全仓，不把 invalidation 说成清空所有缓存。不能凭同 key 自动证明运行请求成功。

## 案例 2：完整 library 文档仍然先看位置，再看概念

**原始请求**：“我不懂这个项目的请求封装，给一份学习文档，告诉我如何加同类列表。”

**给定材料**：应用 web 使用真实请求库；已读入口实例、项目封装、列表消费者和相邻列表，部分后端不可见。材料给的文件如下；包与 API 需要再从实际输入核对。

**好的输出组织**：

```text
一份请求库学习指南.md
  目录
  ①相关文件树：入口实例 / api封装 / 列表消费者 / 同类列表
  ②它在项目里负责什么：只讲支持列表读取的概念和版本
  ③真实使用链：页面输入 → 项目Hook → 请求封装 → 返回消费者
  ④API对照：项目封装与底层库分列，常用与实读调用分列
  ⑤按项目方式新增：复用封装、类型、加载/错误处理和同类实现
  ⑥验证前提与未知：后端边界不可见，未运行
```

具体完整内容见 [库学习正例](library-good.md)；树只列存在且读过的角色，缺少测试不补一份虚构测试。

**坏的输出**：先写二十个库 API 和官方 todo demo，把引用树、Provider、Hook、请求分别存四份文件；称所有请求已联调通过。

**问题与验收**：用户应能指出哪层封装优先复用、同类页面在哪里、输入输出经过哪些可见位置。只列官方 API 不能满足项目用法；每个用途与位置有依据。

## 案例 3：同仓不同应用、不同库代际

**原始请求**：“解释 studio 的路由，别按 admin 的写法讲。”

**给定材料**：studio 清单声明 Router 6，实读 `Routes/Route` 与 `element`；admin 声明 Router 5，实读 `Switch/Route` 与 `component`。只给声明范围，未给锁文件。

**好的输出**：

> 本轮限定 studio。它采用这份源码中的 `Routes/Route` 与 `element` 结构，声明范围属于 Router 6；精确安装版本尚未确认。admin 是另一应用的旧结构，可以对照，但不能把它的 `Switch/component` 示例当作 studio 的新增路由规范。

随后只画 studio 的入口→Router 包装→路由配置→页面映射，给 studio 实读位置与同类路由。框架 API 的完整语义从对应官方版本核对。

**坏的输出**：“整个 monorepo 都使用 Router 6.30.1；请参考 admin 的 Switch 添加 component。”

**问题与验收**：主应用、声明/解析版本、结构分支清楚；不能合并不同应用或编精确版本。新需求示例来自目标应用。

## 案例 4：动态物料只有加载契约

**原始请求**：“我只想先知道组件在哪里渲染，不需要讲全部节点算法。”

**给定材料**：已读画布按图层映射、加载器按标识与版本获得组件、包装器传 props；实际物料源码来自缺失的外部包。没有触发运行或网络下载。

**好的输出**：

> 当前可见路径是“图层集合 → 按标识/版本加载组件 → 包装层传入属性 → 画布展示”。先读图层映射、加载器和包装器这三个位置，就能找到新增渲染参数的消费边界。物料内部怎样处理 props 尚不可见，不把它补成完整渲染生命周期；首轮暂不展开节点算法。

给三处实读位置与箭头条件，缺失处用“动态物料内部待确认”。

**坏的输出**：“模型经内部 diff 算法递归更新每个节点，完成数据库保存”，随后默认遍历依赖、下载私有包、展开所有 effect。

**问题与验收**：能定位核心能力，不假造算法/保存/生命周期。缺失源码在主文可见，不藏进一个附录脚注。

## 案例 5：内部 library → 返回需求定位

**原始请求序列**：①“列表加筛选，哪里改？”②“这里的状态库我不懂。”③“懂了，返回刚才需求。”

**给定材料**：已知列表页面、筛选 UI、store 动作、服务入参、同类页面；有当前阅读历史；期间代码未确认变化。

**好的连续结果**：

1. 先给定位卡：页面/筛选组件候选、动作/服务复核、同类筛选例子、空结果验证前提。
2. library 沿用列表和当前版本；先相关文件树，解释该动作如何连接消费者。只需要局部概念时不用全库长文。
3. 返回原定位卡：说明这次理解帮助决定是否复用现有动作；沿历史回到筛选入口，复核位置后继续。

**坏的结果**：每次重扫 monorepo；默认安装第二个 skill；返回时忘记主应用，生成全仓新地图。

**问题与验收**：原目标、应用、版本和位置不断链。加载资料不触发新线程或另一个 Agent；用户不必重新解释需求。

## 案例 6：刷新不是机械改行号

**原始请求**：“请求封装移动到 shared 了，帮我更新现有指南，保留我的笔记。”

**给定材料**：原指南含旧路径、入口 Provider 与请求链；变更给新文件、调用更新和一个新参数，但未给全部外部消费者；用户笔记另有标记。

**好的结果**：复读新封装与当前调用，更新受影响章节、图下位置和参数解释；保留个人笔记，明确外部消费者未覆盖。没有证据证明 Provider 关系未变时标待复核，不保留旧完整结论。

**坏的结果**：全文替换字符串就称“全仓知识已同步”；覆盖用户笔记；生成第二份 start-here 保留两个入口。

**问题与验收**：旧路径、旧语义和未知各有处理；保存只作用于要求的资料。链接检查通过不等于间接调用行为已验证。

## 案例 7：换画风不换架构

**原始请求**：“把刚才入口结构图改成正式平面风，时序图保持普通。”

**给定材料**：已核对的入口/全局包装/导航/页面四个节点；一个动态跳未知；只有 Mermaid 工具，没有图片产出。

**好的结果**：保持节点、关系与未知；按清晰平面风调布局/标签/颜色，时序保持清晰技术风。输出 Mermaid 源码或宿主实际支持的呈现，说明未生成 PNG；保留相同源码映射。

**坏的结果**：“已生成可编辑 PPT”，新增数据库节点和调用箭头，以暗色装饰消除未知虚线。

**问题与验收**：风格不补事实，产出类型准确。图片、Mermaid 与原生 PPT 对象不同；没有实际渲染不得声称看图检查通过。

## 案例 8：有明确需求，不先上框架课

**原始请求**：“新增一个列表字段，先告诉我改哪几处，按项目现有方式做。”

**给定材料**：当前目标已是 web；列定义、数据类型与相邻字段可见；响应来源尚未确认新字段。

**好的结果**：按列/UI、类型、数据来源给“应改/应复核/外部边界”定位卡，引用相邻字段和样式约定，列展示/空值/数据契约验证。新字段未在响应证据中出现就明确待确认，不默认启动项目。

**坏的结果**：先讲 React 从诞生到 hooks，要求读完十二份指南；声称后台已经返回该字段；直接升级表格库。

**问题与验收**：用户迅速得到改动位置和项目例子，必要未知不掩盖。规范来源真实，定位不等于需求已实现。

## 维护者怎样记录实际验收

可在项目外的本地测试记录中用一张表记：案例 ID、原始请求/输入版本、宿主、实际输出位置、看到的行为、偏差、已执行操作、结论。没有运行的案例写“待执行”，不要填预期答案冒充结果。

分别验证局部范围、证据强度、版本、可开发性、衔接和文件粒度。复制安装/链接检查证明资源自包含；扫描器单元测试证明机械边界；真实 Agent 运行才有行为验收依据。这三种检查不能相互替代。
