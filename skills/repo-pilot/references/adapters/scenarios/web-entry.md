# SOP 2 — 从入口看清页面与产品能力

## 使用时机与完成效果

已经有主应用地图，接下来建立“真实挂载→全局能力→路由/外壳→页面→功能模块”。这一段回答产品在哪些文件被组装、渲染和操作，不展开坐标数学、节点算法或状态迁移的完整实现。

按 E1→E2→E3→E4→E5 执行。先加载一种实际规则：[React](../frameworks/react.md)、[Vue](../frameworks/vue.md)、[React Native](../frameworks/react-native.md)、[Unity](../frameworks/unity.md)。下面用 React Web 举操作例；其他分支用各自规则替换 E1～E4 的具体查法，不能强找 DOM/return/Router。E5 的能力位置与深度边界共同复用。

| 共同任务 | React Web | Vue Web | React Native | Unity |
| --- | --- | --- | --- | --- |
| E1 入口证据 | 构建/HTML→挂载或框架入口 | 创建/插件→mount或框架入口 | 注册/Expo入口→根组件 | 启动配置/场景→对象/组件 |
| E2 全局与结构 | return/Provider | template/render、插件/注入 | return/全局包装 | 对象层级、UI组件、序列化依赖 |
| E3 导航外壳 | Router/Outlet/Layout | RouterView/slot/Layout | Navigator/文件路由/Screen | 场景加载/UI管理器/面板 |
| E4 页面与动作 | JSX块、props/Hook/store | 模板块、props/emit/composable | 原生组件、params/平台模块 | Canvas/UIDocument/Prefab/脚本事件 |

通过条件也使用真实分支：Unity不必证明一条URL路由，必须证明用户入口到UI/脚本；原生应用不必找浏览器代理。

## E1：证明真正入口，处理薄入口

输入：构建配置文本、HTML候选、挂载候选。

怎么做：

1. 从 dev/build 指向的配置看 root、HTML/入口插件和别名。配置只读取，不 import/require 执行。
2. 找 HTML模块标签或插件 entry，随后核对 createRoot/hydrateRoot/旧 render 与 DOM根。main、App、index只是候选名。
3. 文件若仅导出、重导出或 import 另一入口，跟一跳到真实挂载；保留完整短链，而不是略过薄入口。
4. 多个挂载根分别标应用/模式，选当前目标一条；缓存或页面初始化包装不等于挂载。
5. 默认只查应用源码和指定配置，不进依赖内部搜索全部“render”。

记录“构建/HTML来源 → 模块文件 → 挂载API/容器 → 根组件”。每段有真实位置和关系类型。

通过条件：能够解释为什么这个文件是真入口；只有“通常项目用main.tsx”不通过。入口由框架生成则写明真实约定和已确认范围，不编造生成文件。

## E2：先画 return，再概括必要初始化

输入：根组件完整相关 return、Provider 创建位置和必要分支。

读取顺序：

1. 找组件最终 return，压成有缩进的树：Provider、Router、Layout、页面和children；兄弟节点保持兄弟，条件节点注明条件。
2. 再查同一组件提前 return：loading、错误、无权限、重定向、空值；注明正常页面何时出现。
3. 对Provider只补完成结构理解所需的内容：提供什么实例/值、在哪创建、消费者是谁、是否持久化/初始化。
4. 对初始化只概括必要前提：平台配置/用户/空间、关键effect、恢复、事件监听与清理。不要逐行解释无关effect。
5. 存在createPortal或另一个挂载根时标实际边界；import不证明处于同一个渲染树。

Provider记录格式：

| 包裹层 | 给下层什么 | 创建/来源 | 关键前提 | 位置 |
| --- | --- | --- | --- | --- |
| 实际Provider | store/query client/主题/业务context等 | 实例/props/初始化Hook | 例如配置成功/持久化恢复 | 实际证据 |

解释顺序采用“这层解决什么→下面谁需要→前提/失败时怎样”。树是渲染关系，不是每次运行的时序图。

通过条件：用户能说清页面外面包了什么，以及为什么可能先看到加载/异常；只读return而忽略影响页面出现的初始化不通过，深入每个Provider内部也不属于首轮目标。

## E3：路由→守卫→Layout→插槽

输入：真实路由声明、目标路径和根结构。

怎么做：

1. 看项目实际路由版本/API：对象路由与RouterProvider、JSX Route/Switch、useRoutes或框架文件路由分别读，不能套同一版本写法。
2. 记录logical path、basename、path params、query、重定向、懒加载和守卫。域名/环境值未知就保留逻辑路径。
3. 跟element/component/render或懒加载import到真实页面；遇到index重导出，再定位实现。
4. 跟父级Layout的children和Outlet等插槽到页面；画共同外壳与目标子页面，不把每条路由所有包装复制成大图。
5. 权限守卫只说明它读什么、放行/空值/重定向的关键条件；前端没包某个守卫不证明后端无鉴权。
6. 先解释导航或目标最相关的一条路由，再列其他主要路径。不要生成全量路由后不给典型例子。

记录：

| 用户入口/URL | 路由定义 | 外壳/守卫 | 页面实现 | 主要组件 |
| --- | --- | --- | --- | --- |

通过条件：至少一条“URL→路由→Layout/插槽→页面”连续可定位。动态规则或缺源码导致断点时明确停在该处。

## E4：页面结构和数据方向，少读函数

输入：选定典型页面、return、主要组件import及直接数据来源。

怎么做：

1. 把页面划为内容块：工具栏、筛选、列表/画布、详情/属性、弹层、加载/空态。
2. 列每块的组件和文件，优先看props名与父页面的状态来源；不要求逐个子组件展开。
3. 区分页面自己维护的交互state、全局store/context、服务端缓存；说清“谁给数据、谁触发更新”。
4. 找一个常见动作入口（修改标题、提交表单、选择物料等），这里只标处理函数/Hook与大致目的；后续需求定位再读相关实现。
5. 一个组件上千行时先读import、组件签名、正常/提前return和目标动作附近；没有读取的区域不声称全面分析。
6. 同名组件必须按import/别名确定实现，不能按文件名拼接两套渲染链。

输出一个页面的结构树与一张“块—实现—输入/动作—用途”小表。业务能力特别复杂时把内部实现标为深度分析入口。

通过条件：用户不读每个回调也能解释页面有哪些部分；只列文件路径或泛讲React概念不通过。

## E5：产品特征→能力位置→依赖

输入：产品地图、E4页面块、能力实现入口/直接import。

对于可视化编辑平台至少区分：

| 能力 | 首轮要确认的入口 | 应说明到什么程度 | 深度分析才展开 |
| --- | --- | --- | --- |
| 拖入物料 | 物料源/放置区/创建动作候选 | 用哪个库，源和目标在哪，创建链已确认到哪 | 坐标转换、取消、冲突与全部事件时序 |
| 移动画布/改尺寸 | 层包装/画布操作器 | 使用何种包装与库，状态写入边界 | 缩放/吸附/多选算法 |
| 展示渲染 | 层模型→组件映射→实际组件/动态加载入口 | 配置和数据大致如何成为界面 | 物料生命周期、缓存更新、调度与性能 |
| 属性配置 | 配置面板、表单/schema入口 | 谁生成字段、修改值交给谁 | schema求值和状态合并完整实现 |
| 节点/连线 | 节点画布、类型映射、事件回调 | 图节点与大屏组件的边界、相关库 | 连线执行、传播规则、循环和节点变化 |
| 预览/发布/协作 | 对应路由/服务/Socket入口 | 哪个模块负责、哪些服务联系待确认 | 跨端同步、服务消费和发布流程运行行为 |

一般业务项目没有这些能力就按实际功能换行，不给普通管理后台硬套低代码章节。多个拖拽库分任务解释；声明包与直接使用API分开；动态加载物料是静态import索引的覆盖边界。

核心库在能力旁讲：一句话用途＋白话概念＋项目声明版本＋已看到的API＋使用位置。官方资料按匹配版本查，不上传项目代码/部署配置，不批量外发依赖清单。陌生库不能确定用途就标未知；首轮重点解释已确认的核心库。

终端单独核对独立路由、布局/viewport、输入处理、样式和构建目标。移动业务“管理页”不等于手机消费页；2B不等于桌面；HTML5Backend不足以证明触摸支持。

通过条件：用户能回答“产品最主要能力是什么、我应该在哪找、关联什么库”。能够指出渲染入口就先交付，不强迫完成全渲染内部追踪。
