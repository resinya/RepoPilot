# 项目地图协议

建立地图的目标是**可导航**，不是完整。一张好的地图能让使用者自己找到想去的地方，而不是替他看完所有代码。

## 第一步：找入口（不超过 5 次文件读取）

按以下顺序找，命中即停：

1. 依赖清单 —— `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml`
2. 构建与启动配置 —— 依赖清单里的 `scripts` / `entry` 字段，`Makefile`、`Dockerfile`、CI 配置
3. 源码入口 —— `src/main.*`、`src/index.*`、`cmd/`、`app/`、`main.py`
4. 路由或控制器目录 —— 决定了业务模块的切分方式
5. 配置与环境样例 —— `.env.example`、`config/`、`settings.*`

禁止在这一步读取任何实现细节。

## 第二步：画分层地图

输出一棵带职责标注的目录树，只保留三层以内的关键目录，其余折叠为 `…`：

```
src/
├── app/          # 路由与页面（Next.js App Router）
├── lib/          # 共享逻辑与配置中枢
├── components/   # UI 组件
└── proxy.ts      # 请求入口（Next 16 起 middleware.ts 改名）
```

每个目录的标注必须是**从实际引用关系得出的**，不能从目录名推断。没有把握时写「待确认」。

## 第三步：标注三类边界

| 边界类型 | 要回答的问题 |
| --- | --- |
| 外部依赖边界 | 这个项目调用了哪些外部服务？凭证从哪里读？ |
| 数据边界 | 数据落在哪里？有几个数据源？是否有缓存层？ |
| 构建与部署边界 | 怎么构建？怎么部署？环境变量在哪个环节注入？ |

## 常见失败模式

- **一步到位综合征**：试图在第一轮就解释完整个仓库，结果是泛泛而谈。
- **目录名即职责**：把 `utils/`、`common/`、`helpers/` 当成无业务代码跳过，往往错过真正的逻辑。
- **只看 README**：README 经常过期。以代码和配置文件为准，README 只作为线索。
- **忽略测试目录**：`tests/`、`e2e/` 往往是理解业务边界最快的材料。

## 收尾要求

地图交付时必须同时说明：

1. 读了哪些文件（列出路径）
2. 哪些目录未覆盖
3. 哪些职责标注属于推断（无引用证据支撑）
