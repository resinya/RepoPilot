# 讲解契约 — 骨架优先、讲透配置与模块

## 何时读

解释源码节点、配置文件、依赖注入模块，或开始 walkthrough / teach / deep / library 前读取。只在命中下列情形时应用对应原则，不无差别套到所有输出：遇到配置或配置函数、依赖注入模块（@Module 等）、框架样板文件，或用户表示不熟悉某项技术时。

## 原则一：骨架优先，再叠业务

解释框架样板文件（NestJS 的 @Module、React 组件、CLI 入口等）时，先给**最小可运行语法**，再逐层叠加 imports / hooks / 三方库 API，并明确标注哪些是框架默认、哪些是项目业务。

模式：
1. 先给裸骨架（只有框架必要结构，无业务）：
```ts
// 最小骨架：只有框架要求的结构，没有任何业务
@Module({})
export class AppModule {}
```
2. 再给叠加业务后的样子，逐行注释哪些是默认、哪些是新增：
```ts
@Module({
  imports: [ConfigModule, UserModule], // 项目新增：引入其它模块
  controllers: [AuthController],      // 项目新增：注册控制器（接收请求）
  providers: [AuthService],           // 项目新增：注册服务（处理业务）
})
export class AppModule {}
```
3. 收尾明确：框架默认部分负责什么、业务叠加部分负责什么、为何这么分工。

完成条件：读者能分开“哪些是框架给的”“哪些是项目加的”；不把 import 的三方库当成框架内置，也不把项目覆写当成框架默认。

## 原则二：区分框架默认配置与项目层层封装

配置常是框架默认被项目多层包装。先给**框架默认配置（骨架/趋势）**，再给**项目封装层**，逐层标注哪一层在覆写、为什么。

模式：
1. 先列框架开箱默认（趋势）：
```ts
// 框架默认：ConfigModule 无参 forRoot 即读取 process.env 全部变量
ConfigModule.forRoot()
```
2. 再给项目封装，指明覆写点：
```ts
ConfigModule.forRoot({
  isGlobal: true,               // 项目覆写：全局可用，不用每模块重复 import
  load: [configuration],        // 项目覆写：额外加载配置工厂
  validationSchema: envSchema,  // 项目覆写：启动时校验环境变量
})
```
完成条件：不把项目覆写当成框架默认；不把默认当成项目实现。每一层包装说明它解决了什么（全局可用 / 校验 / 分层）。

## 原则三：配置必须枚举实际字段

遇到配置，必须给出**实际字段名 + 含义注释 + 示例值**，用代码块或表格，而不是抽象的“包含用户与密码配置”。模板见 [config-guide](../../assets/templates/config-guide.md)。

```ts
username         // 用于登录的用户昵称
defaultPassword  // 系统登录的默认密码
tokenExpiresIn   // 登录令牌有效期（秒）
```
字段来源（env / yaml / 默认值 / 配置工厂）一并标出。

### 配置函数剖析（selectConfig / registerAs / forFeature 之类）

对每个配置取出 / 注册函数，按以下四问剖析，并判断它是否框架内置：
- **是否内置**：查官方类型签名 / 文档确认；项目自定义包装另标。
- **入参**：什么类型、代表什么（模块 vs 配置形状 / Token）。
- **出参**：什么类型、能在哪里消费。
- **数据流**：env / yaml / 默认值 → 在哪注册 → 在哪取出 → 在哪注入使用。
- **配置内部流程**：配置文件自身的加载顺序、合并、覆写、生效点。

完成条件：用户知道“传什么、出什么、怎么起作用”，而不是只知道“这是配置”。

## 原则四：技术栈前置简报（走流程前）

走读 walkthrough、带教 teach、机制 deep 或单库 library 前，若流程会用到用户可能不熟悉的技术栈：
1. **列出本流程会用到的技术栈**（3～6 个，按角色）。
2. **询问用户哪些不会**（一次聚焦问题，不穷举全栈）。
3. 用户指明后，对其做**简报**：白话概念 → 在本项目怎么用 → 常用 API（5～8 个）→ 调用关系 → 给出该技术栈的**使用流程图**（Mermaid）。
4. 简报完成再进入原流程；简报已达到 library 深度时转完整 library 流程。

完成条件：读者对要走读的代码“用什么技术、这些技术在本项目怎么用”有前置认知，不盲目前进。简报不替代原流程，也不自动改装 / 启动。
