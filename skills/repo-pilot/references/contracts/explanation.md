# 讲解契约：业务优先，按需拆代码

用于 business、walkthrough、trace、teach、deep、library 的解释。目标是让读者沿一个问题形成连续认知；同一问题的职责、流程、数据和证据放在一起，不迫使用户在多文档、页面或弹窗之间拼答案。

## 1. 先讲职责和数据

先用一句话解释用户目标或当前业务步骤，然后按“输入来源 → 处理/条件 → 输出 → 消费者”展开。模块和函数名作为定位信息，不能代替业务解释。区分包含、依赖、调用、数据流；注册列表不是执行顺序。

业务框架是职责分工，技术框架是承载代码的机制。用户“先理解框架、分模块、先讲业务”优先交业务能力地图，除非明确询问技术框架。

## 2. 小切片优先，骨架只在需要时给

Agent 要读够相关源码，展示却只保留本轮问题需要的几行。链式表达式可以拆成有注释的等价讲解写法，必须标为讲解改写，不声称源文件长这样。

用户不理解框架样板时，可以给最小语法骨架，再标出项目新增；无需每次都重复骨架。例：`@Module` 是 Nest 注册模块元数据的装饰器，`controllers` 登记请求入口，`providers` 登记可注入对象；注册不等于依次执行它们。React 的 Provider 包裹和 return 结构同理。

骨架可能只是语法示意，不能称其可独立运行。框架内置、第三方包、项目封装必须按真实 import 来源和定义区分；不能因为函数在配置目录使用就认定是项目自定义。

## 3. 配置解释服从当前问题

只需要整体认知时说明配置来源、用途、生效点及影响当前业务的分支。用户要详细配置才列本次相关实际字段、含义、来源、默认/覆盖条件、消费者；未知写未知，示例用安全合成值，不读真实环境和密钥。

配置函数按四问：来自哪个库/项目定义、入参是什么、返回什么、怎样消费。进一步需要时追加载→合并/校验→注册→取出→消费者。不要写框架默认行为或签名的推测；若需核对官方信息，按目标版本查权威文档。

用户明确“配置不用细看”立即回业务主线，不用契约当理由继续枚举。

只有用户要求配置详情时，按[配置说明模板](../../assets/templates/config-guide.md)在当前文档集中展开，不默认新增子文档。

## 4. 技术预备与场景解释

首次项目/新模块分析按 [demo](../workflows/demo.md) 列相关技术和包关系、必须询问熟悉度；陌生项先给完整最小 Demo，再接续原目标。用户已明确熟悉/跳过或只问单点、沿原节点继续时不重复问。预备范围限于当前主线，不逐一调查所有传递依赖。

带读中新出现的陌生技术先一句白话概念、本项目职责和位置；用户需要基础学习则带当前问题切 demo，完成后返回。简报与几行骨架不能冒充完整可运行 Demo。

完整项目单库学习转 library，最小基础实现转 demo，保留当前应用/版本与问题。技术资料查询只发通用包名和必要版本。

## 5. 连贯交付与控制

完整问题先交完整业务答案；交互带读则每轮一个小问题。默认不要求考试、不自动标记理解完成。保留继续、跳过、返回、切模块的用户控制，不要求反复确认。

数据传递可视化先用一个连续案例和固定参与者的时序图讲谁传给谁，再按较大阶段把数据样子、来源、处理结果与文件作用放在一起；不能每个内部动作拆一页。阶段导航只定位/高亮，不隐藏其他核心信息。配置/存储/本步生成值不能当作发送方自己输入；来源可收起，算法与长API表按需展开。

[业务学习正反例](../examples/business-learning.md)校准整体与小步节奏；[配置讲解示意](../examples/explanation-good.md)仅用于详细配置请求；[集中地图正反例](../examples/interactive-map.md)校准页面交付。
