# 任务衔接 — 复用上下文，保持问题连续

## 什么时候读

从主流程切到 library/deep、跨应用、局部追问或恢复旧目标时读取。简单的单点解释直接应用相关原则，不强制填写全部字段。具体步骤属于对应 workflow；文件与元数据遵循 [输出契约](outputs.md)，合格标准遵循 [质量契约](quality.md)。本文只补上下文衔接，不另定文件命名或评分体系。

## 开始：先确定这轮要解决什么

从用户输入和已有会话提取以下上下文，缺失的可先定位；只有歧义会改变目标应用或做法时才问。通常用一句进度说明即可，不向用户输出一堆内部字段。

| 上下文 | 作用 |
| --- | --- |
| 目标与产出 | 建立整体认知、找需求位置、学包用法或解释具体机制；回复、保存或修改现有章节 |
| 范围 | 仓库根、主应用、辅助应用、终端；其他应用不因同仓而自动变成主线 |
| 当前依据 | 已读文件/符号/行号、声明版本、可得解析版本、地图/报告日期；复核旧位置 |
| 当前问题与位置 | 一个页面、包、动作或断点；已有阅读历史不要丢 |
| 可见与未知 | 源码可见/动态/外部边界、尚未确认关系、已排除和未读范围 |
| 实际操作状态 | 静态读取、用户报告、实际执行分别记；请求学习不等于请求安装/启动 |

不要把这张表变成必须落盘的 JSON 或一个后台状态服务。跨会话需要保存时使用 [知识约定](knowledge.md)，只保存实际需要的 Markdown。

## 各流程最低交付与停点

| 流程 | 足够开始的输入 | 完成时至少有 | 到哪里停止 |
| --- | --- | --- | --- |
| onboard | 仓库和新人目标；应用可先发现 | 产品/职责地图、架构与技术角色、入口到结果/页面/场景、重要位置、开发路线与未知；有需求补定位卡 | 用户能定位开发起点；不默认展开库内部、全部业务或算法 |
| map | 仓库或已知应用 | 分工、核心目录、关键结构关系、证据、下一阅读位置 | 不冒充已解释全部业务或代码审查 |
| architecture | 应用/成员、入口与已读结构 | 工程/运行/代码/数据四维判断与依据；缺口保留 | 不用 monorepo/目录名或某个库替代架构证明 |
| stack | 限定范围的清单、配置、使用线索 | 技术按职责、应用和版本解释，声明与实读使用区分 | 不生成全库百科或升级方案 |
| business | 一个应用/功能和用户目标，复用已有地图 | 能力分工、一个场景、输入/处理/输出、需求起点 | 不默认展开每个函数或混合多套实现 |
| visualize | 业务范围、已读节点/链路或可补读源码 | 同页职责、完整场景、字段变化、文件作用与未知 | 不强制层层点开，不运行目标业务或默认发布 |
| standards | 当前应用与开发目标 | 明文规范/观察习惯、项目例子、命令目录与前提 | 不因列出命令而执行，不将官方最佳实践冒充团队规则 |
| locate | 具体需求或明确的学习示例 | 业务锚点→页面→改动候选/复核位置，同类实现、项目约定、验证前提、断点 | 定位卡完成；只请求定位时不修改或启动 |
| library | 库/技术栈和应用或消费者 | 引用树、白话概念、版本、一个实读使用链、常用/实际 API 区分、项目例子/扩展方式 | 项目用法讲清；算法/内部生命周期需要 deep；用户只问一个 API 则局部回答 |
| deep | 一个动作/机制与已知入口 | 触发→调用/状态前后→消费者/生命周期、条件、证据、无法确认处 | 该动作到明确终点或可见边界；不无限追第三方内部 |
| trace | 一个业务/命令/任务动作 | 相关跨层关系、条件、逐跳位置与外部断点 | 不把可见静态路径提升为服务实际调用成功 |
| walkthrough | 当前目标与真实位置 | 一个节点、上下游、与原目标联系、下一方向 | 默认一个节点，不追完所有分支 |
| teach | 已定位代码、用户学习目标 | 观察→理解→练习，项目例子与完成条件 | 展示不等于掌握；实际反馈与运行分开 |
| refresh | 原报告/记录与变更范围 | 被影响的章节/关系、已复核来源、保留笔记、仍待复核项 | 本轮覆盖内更新完成；不能保证所有间接影响都已发现 |

最低交付允许限定结果：关键跳缺源码时画出已知部分并说明断点、所需材料和下一定位方式。缺少材料不等于整轮不能给任何有用结果；也不能拿一条候选链假称闭环。

## 流程切换：读取规则，不重开一套项目

1. 先完成当前能回答的部分，给已确认位置与缺口。
2. 依用户意图切到对应 workflow，沿用目标应用、版本、入口、阅读历史和当前问题；只补读缺少的证据。
3. 当前流程拥有自己的结论和交付。框架适配只决定怎样读结构，不改变任务；输出模板只组织信息，不生成事实。
4. 完成后回到原目标，说明这次解答的关联与一个下一位置。返回依据阅读历史；切换同一节点的关系视角不丢当前位置。
5. 用户只问一个局部问题就给局部结果。不要自动生成 overview、API 文档、工作日志和一套图；用户要求完整学习文档时才采用完整 library 结构。

示例：上手看到“渲染入口”→用户问“这个状态库在这里怎么用”→携带当前画布、实际包版本与消费符号进入 library→说明相关 store/API/订阅使用链→返回“新增属性面板应沿用哪处更新动作”。用户进一步问订阅变化如何传播时再进入 deep。

这一切由同一 Skill、同一 Agent 执行。资料链接、related 列表、任务参数均不自动创建线程/子 Agent，也不是调用另一套安装包。只有已存在的用户授权才支持额外工具操作。

## 内容所有权：一个事实有一个主要维护位置

- 主概览维护产品分工、能力位置、规范和阅读路线；没有必要把完整库手册粘回概览。
- 库学习维护该库在限定应用/版本里的用法；概览保留短卡和需要的链接。
- 机制分析维护一个具体动作的深度证据；主文保留机制入口、大致方向与重要边界。
- 附录保留可独立查表的全量依赖、命令或证据。当前未知会影响主线时必须在主文可见。
- 变更时先修改/合并已有章节，检查同义重复与旧链接，再增加资料。保留用户笔记，不维护两个互相矛盾的主入口。

## 切换后的检查

按证据、输出和质量契约执行检查；这里补充切换后的检查点：

- 新流程使用当前应用与版本，而非另一个应用的示例。
- 旧引用复核后再引用，断点没有因图表或模板填充而消失。
- 内容更新在输出契约规定的主要位置，不生成另一套重复指南。
- 返回原目标时能说明“刚才的解答怎样帮助下一步”，不是只交一个库百科。
- 用户理解来自实际反馈；链接检查、文档存在都不能证明内容正确或用户掌握。

无法补齐时明确“本轮限定范围交付”及具体缺口，不宣布全仓分析完成。最后用简短说明给成果路径/结果、覆盖与未执行项、最相关的下一步；不额外生成一份质量报告来重复主文，确有审阅需求才保存。
